# MIDI and MTC logic

This independent crate ports the pinned source's MIDI value and MTC state logic. It does not enumerate OS devices, bind a physical/virtual MIDI port, schedule output, or wire the native host/UI. There is no placeholder native backend returning fabricated device lists or claiming delivery. The retained Svelte MIDI actions and timecode consumers remain unchanged.

The oracle is FreeShow commit `2d94defcf98175e4f5c9504e7f4fd1d33c35c975`, version `1.6.7-beta.2`: `src/electron/utils/midi.ts`, `src/electron/timecode/MTC.ts`, and `timecode.ts`. Tests execute those actual function declarations with controlled port/clock boundaries and the installed `JZZ@1.9.5` packet constructors and message descriptions. `NOTICE` records its source hash and MIT license.

## Native integration API

All operations are pure, synchronous, bounded transformations/bookkeeping. There is no filesystem, runtime, timer, OS thread, subprocess, global queue, or device IO in the crate. A future native backend must own real OS handles on a bounded IO owner and provide one ordered stream per device.

| API                                                           | Contract                                                                                                                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `device_names(&[Value]) -> Result<WireData>`                  | Projects ordered device info into `{name}` values, retaining duplicate names, Unicode spelling and own undefined names. Host must supply actual backend enumeration.                       |
| `prepare_send(&mut Value) -> Result<SendPlan>`                | Applies the source defaults and in-place channel decrement, retaining unrelated fields. Does not claim a port opened.                                                                      |
| `SendPlan::packet() -> Result<[u8;3]>`                        | Constructs/validates the actual control, note-on or note-off packet with JZZ-equivalent errors. **Call after successful backend output open/reuse** to retain the source's error ordering. |
| `receive(id, bytes, description) -> Result<Option<WireData>>` | Transforms one original/JZZ-described message into the original `RECEIVE_MIDI2` data. `None` means the source emits nothing.                                                               |
| `mtc_packets(time_ms, fps) -> [[u8;2];8]`                     | Constructs eight quarter frames in source order. It neither opens a port nor sends/schedules those frames.                                                                                 |
| `MtcReceiver::feed(bytes, now_ms)`                            | Updates fixed receiver state and returns up to two ordered `TimecodeEffect`s. `now_ms` uses `Date.now()` units; no wall clock is consulted.                                                |
| `StatusGate::update(status)`                                  | Reproduces `timecode.ts`'s shared persistent status suppression. Keep one gate across timecode modes, not one per message or listener.                                                     |
| `PortBindings`                                                | Minimal native-owned source cache bookkeeping described below; opaque tokens are not deserializable and do not stand in for real OS handles.                                               |

`WireData {data, hydration}` preserves JS transport values. Assign `undefined` at each `hydration.undefinedPaths` pointer, rather than deleting the property/index. `hydration.numbers` contains `{path, number}` entries. `Number` is explicitly tagged as `Finite(value)`, `NaN`, `PositiveInfinity`, `NegativeInfinity`, or `NegativeZero`; it never silently collapses special values to JSON null. The `SendPlan` hydration describes its private mutated send input. `receive` hydration describes the renderer callback payload. Native integration must validate its captured context before publishing/hydrating events.

MIDI receive effects route to main's original `ToMain.RECEIVE_MIDI2` as `{id, values, type}`. MTC `Frame(Number)` routes through `processFrame` to `Main.TIMECODE_VALUE`; `Status` routes through the shared gate to `Main.TIMECODE_STATUS`. Undefined/non-finite values must be restored or explicitly diagnosed by the host transport before retained callbacks run. No bridge code is changed by this slice.

## MIDI details and port ownership

Falsy `type` defaults to `noteon`; falsy `values` receives source defaults. A truthy channel is decremented in-place before opening the output. Numeric channel zero stays zero; string `"0"` becomes minus one and fails JZZ validation. Numeric strings, hexadecimal channel/controller strings, booleans/null, array coercions and default/missing velocities retain the covered JZZ semantics. Missing note-on velocity defaults to 127; note-off defaults to 64. A wholly missing `values` instead supplies velocity zero. Unknown truthy types select note-off, exactly as the source fallback does. Note-name aliases include JZZ's own octave numbering, H, natural/flat/sharp/double-accidental spellings and Unicode accidentals; the frontend's display octave convention is separate.

Packet validation errors retain actual JZZ `RangeError`/`TypeError` names and messages for supported scalar/coercion cases. The original `sendMidi` catches/logs these errors without a success/failure reply; the pure API exposes them for the host to diagnose. Backend open failure must prevent packet validation and must not insert a cached output; later sends retry the open. The source opens/reuses before validation and keeps ordinary output ports open between sends.

`receive` requires the **actual source-equivalent description string**, not a fabricated generic label. The source branches on `toString().includes("Note")`, `"Off"`, and `"Control"` as well as status bytes. Actual JZZ velocity-zero Note On describes Note Off. A label containing `Note Off` can also make an aftertouch message take the note-off branch. Short messages can emit own undefined note/velocity/controller/value fields. This crate does not port JZZ's complete manufacturer/SysEx/SMF string formatter, so native bytes alone do not establish parity for arbitrary labels and described system-exclusive messages. A future backend must supply a verified description adapter or explicitly gate those variants.

`PortBindings` stores at most 32 logical input/output/MTC tokens combined. `listen` preserves input-ID deduplication and the literal `"input"` sentinel. `opened_input`/`opened_output`/`opened_mtc_output` are trusted host acknowledgements **after real opens succeed**, not public IPC commands. Host retains the real handles separately; it must serialize opens and count in-progress/failed-close handles against its own capacity. The book does not create a generic backend or spawn work.

`close_inputs(id, close)` preserves the source quirk that an unknown nonempty ID closes **all** inputs. A failed specific close leaves its binding, while close-all clears the source map despite individual errors. Numeric property keys close in JavaScript object enumeration order, followed by other insertion-ordered keys. `stop_midi` closes inputs before ordinary outputs and permits future reopening. MTC has its own first-output cache, ignores later output selections until `stop_mtc`, and retains its token if close fails. `shutdown` is an explicit terminal host boundary and invalidates subsequent book operations. Backend close callbacks must run on the future IO owner, honor its bounded lifecycle and return promptly; the planner bounds their invocation count but cannot interrupt arbitrary host callbacks. Failed OS handles still belong to that owner until actually closed; clearing a logical source map does not prove physical closure.

Opaque callback tokens reject callbacks after logical closure or reuse, preventing an old listener token from being repurposed for a new action. The source's unnamed-input leak, callbacks arriving after a failed close-all, inherited/prototype-shadowed output keys, arbitrary JS object methods, and async simultaneous-open races are not claimed as equivalent supported native bindings. Unnamed inputs and custom `toString` coercions are explicit `midi_unsupported` variants. Prototype-shadowed input IDs preserve the source's ignored-listen behavior; unsupported prototype output/close operations are diagnosed. No live OS implementation exists in this slice, so there is no claim of native cancellation, driver shutdown, hotplug, device-name matching or hardware timing parity.

## MTC state and integration boundaries

The receiver retains all eight partial quarter-frame nibbles and emits on type seven without requiring a complete ordered group. FPS comes from embedded quarter/full-frame bits, with exact values 24, 25, 29.97 and 30; the setup function's framerate argument is unused. Full frame recognizes only the source's prefix positions, does not validate device ID/EOX, can produce NaN when truncated, updates the nibble buffer, and emits no play status. Song Position assumes 120 BPM, applies `(sixteenths / 120) * 15000`, and resets the last tick.

Start emits the saved position before play and keeps an earlier song position; Continue only starts the clock and play status. Stop clears the last tick and emits pause. Timing Clock adds deltas strictly below 500 ms when the previous tick was positive; a backward delta is added, while 500 ms or larger is ignored. Every tick updates the last tick and requests play. The shared gate then suppresses repeated statuses as `timecode.ts` does. NaN/Infinity/backward samples are represented explicitly rather than clamped into invented valid timestamps.

Sending preserves `{24:0,25:1,29.97:2,30:3}[fps] || 1`, including the source bug that 24 signals FPS code one. Unknown rates use code one but still participate in frame math. It preserves JavaScript remainder/floor/ToInt32 behavior for negative, large and non-finite numbers. There is no drop-frame correction, quarter-frame timing compensation, or continuous frame-rate scheduler. The original sends all eight immediately on each `updateTimecodeValue` call; the future host must preserve that ordering.

The global timecode router, LTC/ableton/audio decoding, native port open/close and UI integration remain separate. In particular, source `timecodeStop` does not reset the retained `currentMode`, `sendData`, framerate or shared status; a later value update can reopen MTC. The pure packet/receiver APIs do not invent a replacement router or silently fix these persistence quirks.

## Bounds and evidence

Fixed bounds are 1,024 input message bytes; 256 enumerated devices; 4,096 UTF-8 bytes per name/scalar/description; 65,536 aggregate projected-name/JSON bytes; JSON depth eight and 1,024 nodes; and 32 logical port bindings. JSON work is bounded before cloning selected fields. MTC state uses eight nibbles/two numbers; sending always produces eight two-byte packets; receiving produces at most two effects. Close diagnostics are capped at 512 UTF-8 bytes each. Resource violations return `midi_resource_limit`, unsupported variants return explicit diagnostics, and terminal/obsolete bindings return `midi_shutdown`/`midi_closed`. Device metadata objects with non-scalar names are unsupported. These are bounded pure interfaces, not a claim that an unimplemented OS backend is bounded.

The Linux read-only feasibility probe `fs.openSync('/dev/snd/seq', 'r+')` returned **EACCES** for the current unprivileged user. No MIDI message was transmitted. No cached `midir`/`alsa` Rust crate or default/extracted ALSA development package was present, so this slice adds no native dependency or device backend. It never substitutes empty device lists for unsupported enumeration. Windows/macOS real MIDI APIs and hardware remain unverified.

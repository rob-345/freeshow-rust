# Spotify concurrent capability recovery

This follow-up to the command foundation (`88e1dedc`) changes only its private capability bookkeeping. It adds no native command IPC, bridge, thread, task, public reply or backend authority. The original command scheduling reply remains early `true`; direct-child completion still does not certify a Spotify effect.

An entered state query kept its capability snapshot across asynchronous child IO and unconditionally restored that snapshot on completion. A concurrent command could observe the executable genuinely missing and publish `Unavailable`, after which the older state query restored the internal cache to `Ok` without changing the public capability. Later state queries skipped the recovery probe, while command admission continued rejecting the public unavailable state.

Only actual capability observations now update the internal cache and its public projection together, on the existing single owner without an intervening await: startup probe, admitted request reprobe, and state/command executable-spawn failure. Ordinary completion, cancellation before entry, expired admission, source process failure, parse outcome and ready-result disposal do not restore a previous snapshot. Observations settle in actual owner order; this is a cached capability, not a guarantee that a subsequently selected native executable path remains present. Shutdown and panic still reject admission and retain their actual cleanup/join owners.

The new Linux regression uses an immutable executable fixture behind a private Unicode symlink. Its Metadata child writes an entered marker and actually stops itself with `SIGSTOP`. The test witnesses that real child's `/proc` stopped state, removes the executable symlink, accepts a concurrent command and observes its genuine `spotify_binary_unavailable` completion. It then restores the same executable, sends `SIGCONT` through an owned/waited signal helper, and observes the older state query succeed. A subsequent state request must execute the actual help reprobe plus four query children, restore `Available`, and allow a real command child. Final service shutdown proves all eleven spawned direct children were waited and the retained whole-job quota returned to zero. No sleep-only scheduling assertion, desktop bus, account, network or GUI is involved. Failure unwinding closes the actual service before the private fixture is removed.

Against unchanged production code, this test fails at `Unavailable { code: "spotify_binary_unavailable" }` versus `Available` after the subsequent successful state request. Raw evidence remains `/tmp/freeshow-spotify-capability-race-negative.log`. An earlier rejected fixture-observation attempt incorrectly assumed that `/proc/status` was UTF-8: Linux can truncate a Unicode process name mid-codepoint. The test now checks the actual stopped-state bytes. That rejected observation log remains separate and is not counted as the regression proof.

Focused checks use only `/mnt/data/cache/freeshow-rust-build/spotify-capability-race/{check,target}`, Rust 1.99.1, offline dependencies, one Cargo job, debug information disabled and incremental compilation disabled. The external standalone manifest imports this crate's actual source and fixtures; no shared manifest, lock or target changes are required. Native tests: 22 passed, including the existing accepted-receipt Drop, explicit cancellation, aggregate scheduler unwind, anchored child reap, whole-result quota and actual thread-join regressions. The new real race/recovery regression also passed twenty additional executions. Pinned Node 22.21.1 source/private-bus suites: 20 passed, zero skipped, covering existing state, hydration and commands. Strict all-target Clippy passes on Linux and cross-checks Windows GNU/macOS ARM; foreign checks are compile/lint evidence only. Rustfmt and configured Markdown formatting pass.

The foundation remains unwired for `MAIN.SPOTIFY_COMMAND` at this base. Its future native host must keep the bounded request-context/explicit-cancellation registry described in [spotify-commands.md](spotify-commands.md), preserve early replies, and retain the actual service through cleanup and join. No packaged GUI, real Spotify account, physical playback or foreign-platform command transport was tested here.

# Idle CPU investigation

This investigates the existing Linux release evidence/current source and one explicitly reserved diagnostic profiling pair. It does not demonstrate an optimization or replace the five-pair baseline. Only this document is added to Git. No archived executable, asset, old raw receipt or shared source was changed; no build was run. The initial inspected root was `2a5019ddb56c9ac97b25117742523c2c49407ba2` plus the coordinator's in-progress ingress tests; the candidate frontend files below are identical to the immutable original and the archived Rust source.

Its immutable executable is `/home/rob-admin/.local/share/freeshow-rust-baselines/c9e62492/freeshow-desktop`, SHA256 `b1924acd481ec61baf80105be0734c4f7805caf64213d82ae0c81eda73909fbf`. It predates most current native services, so newly added native loops cannot explain that historical measurement.

I recomputed per-process deltas from the unchanged ignored directory `test-output-rust/release-comparison-full-20261018`. All ten measured `samples.jsonl` SHA256 values matched [the committed receipt](../baselines/release-idle-editor-linux.json). Each measured run has 42 steady snapshots and a stable set of identities: four Rust processes and nine Electron processes throughout this interval. For these particular records there is no newly born/late identity to infer a starting counter for. Per identity:

```text
CPU ticks = last steady cpuTicks - first steady cpuTicks
CPU seconds = CPU ticks / 100
wall seconds = (last observationEndMs - first monotonicMs) / 1000
percent of one core = CPU seconds / wall seconds * 100
```

## Concrete candidates, not measured causes

1. **Unconditional meter frame loop and repeated identical DOM writes.** `src/frontend/components/output/preview/Preview.svelte:261` mounts `AudioMeter channelId="main" preview` even with no playing media. `AudioMeter.svelte:132–139` immediately schedules another animation frame before its 33 ms throttle; it therefore keeps a frame callback active at the engine's display cadence, while doing meter work around 30 fps. `updateDOM():86–128` writes mask width/height and peak display/position, and adds/removes the active class, even when every raw channel is MIN_DB and the resulting presentation is unchanged. This work is real source behavior on both engines. Different engine handling of frame scheduling, unchanged style writes and repaint is a hypothesis, not the certified explanation of their CPU difference.

    The safest first optimization candidate is to skip identical owned style/class writes while keeping the same analyser polling, smoothing, two-second peak hold/decay, mute logic and frame cadence. A deterministic component test should compare all rendered values to actual original component executions for changing dB, silence, mute, peak release, vertical/horizontal orientation, channel-count changes, replacing bound elements and destruction; a quiet interval should prove zero redundant DOM mutations after initialization. This is a measurable work reduction even if a later real release comparison finds no material CPU change.

    A later scheduler change needs actual input lifecycle knowledge. `getVisualizerData` polls real AnalyserNodes; audio samples can change while no Svelte store changes. Suspending polling merely because the current reading is silent would freeze a live microphone or stream. An idle/no-source path would require trusted analyser/source attachment/removal notifications plus bounded recovery polling, while preserving the active meter cadence and all pending decay. It must not infer inactivity from dB alone, pause active capture/playback, or globally throttle hidden projection windows.

2. **Eager/resumed Web Audio in an otherwise empty window.** `src/frontend/audio/audioAnalyser.ts:21` constructs an AudioContext when the imported class is evaluated. Its `getAudioContext():35–45` resumes suspended contexts. `AudioRoutingManager.init():97–104` subscribes to audioRouting and unconditionally calls `AudioAnalyser.recorderActivate()`, which evaluates `getAudioContext()` before `AudioSender.activate` checks whether any sender should run (`audioAnalyser.ts:464–465`, `audioSender.ts:54–67`). The always-mounted meter's first missing-entry query reaches `AudioRoutingManager.getInstance()` via `audioInputCapture.ts:154–160`. This is a concrete route to creating/resuming audio infrastructure without a playing source; actual context state and which threads consume CPU still need observation. Deferring construction/resume until a real audio consumer needs it is a candidate only after profiling supports it. It requires genuine playback, microphone, analyser, routing, recording, Opus/worklet/port and no-user-gesture behavior checks; a fake backend or silence-only test cannot certify it.

3. **A precreated hidden output may explain the second web process.** The second Rust WebKit web process is born 3.72–3.87 seconds after the native root in every measured run, and consumes 4.58–5.35% of one core. Source `getActiveOutputs()` synthesizes a first default output for an empty configuration (`components/helpers/output.ts:686,705`), while `updateSettings.ts:159–168` schedules `restartOutputs()` after 2.5 seconds even when autoOutput is false. `restartOutputs()` sends CREATE for enabled outputs; native `output.rs` creates a real webview with `visible(false)`. This timing and source path make a hidden output a strong role hypothesis. Raw process argv and the baseline's main-window DOM do not prove that role, however; they contain no per-webview PID/URL mapping. The source already precreates hidden windows and explicitly disables Electron background throttling, so deleting or globally suspending these windows would change first-cue readiness, output messaging, clocks/timers and audio semantics. Inventory actual handles/roles first; if its work is audio, address unnecessary audio work rather than dropping required output ownership.

4. **Condition timers wake even for empty/static content.** `components/output/layers/SlideContent.svelte:80–90` and `Overlay.svelte:43–56` start 100/300 ms intervals even when currentItems has no conditions; the callback checks that fact on every tick. A hidden output plus its main-window preview can multiply this small periodic work. A candidate is to create the same-rate timer only when conditions exist and stop it when they disappear. Tests must cover empty→conditional→empty transitions, microphone-driven 100 ms conditions, ordinary 300 ms conditions, clearing/destruction and actual retained updates. This is lower-frequency than the meter and is not established as a significant share of CPU. `LazyLoad.svelte:14` also retains a loaded component after show becomes false; this can preserve background work after navigation, but cannot explain a fresh baseline that never visited those pages. Blind unmounting can lose retained state and is not proposed.

5. **Current native download workers have an avoidable idle timer, outside the archived cause.** `crates/freeshow-ffmpeg-download/src/service.rs:263–273` starts two fixed network tasks whose select always includes a 20 ms sleep followed by reap, including when there are no jobs. This permits about 100 timer wakeups per second across the two tasks. That is source evidence about scheduling, not measured CPU use. A job/deadline-driven notification and a pending timer while no reapable work exists can remove empty polling, provided new jobs, prepared-job expiry, abandoned/expired cleanup, cancellation, shutdown and actual child/filesystem drain still wake the fixed owners. Tests should hold prepared outputs through TTL, drop accepted callers, admit the first job after a long idle, and require cleanup without a second request. This crate was added after `c9e62492`; optimizing it cannot be presented as explaining the archived regression. Conversely, current ingress's 5 ms loops are bounded lifecycle waits, not unconditional idle loops, and did not exist in the archived binary.

The meter, input-capture, analyser, clock and LazyLoad files are byte-identical across original `2d94defc`, archived source `c9e62492` and inspected current source. For the main candidate, AudioMeter SHA256 is `44118ee444a2320598b84dd9fd7b7e08f0aadc8570dd13b957f8400dcfb1f142`; AudioInputCapture is `eb43640675742ffb1f8f6ce714ac4006bdb81f8cf18f99ebc7516c8619d94d1e`; AudioAnalyser is `ff000b9ddcd06eb88069a210abe09fb293e75a34e116bc702de0045768146eff`. There is no evidence that migration introduced these frontend loops, nor that fewer Rust owner threads would solve them.

## Bounded optimization and verification proposal

The leading next code slice is lazy singleton construction of AudioAnalyser's context, plus checking existing `AudioSender.shouldBeActive()` **before** recorderActivate evaluates/resumes that context. Keep real active-source analysis, playback, microphone, routing, recording, worklet/port metadata/PCM and global native DSP/Opus semantics. Getter/caller conversion must handle existing direct `this.ac` accesses and the redundant `??=` destination-node expression without accidentally creating multiple contexts or recursively rebuilding routing. Do not suspend a real running graph just because its present samples are silent. Keep first use driven by the genuine source operation and do not invent a source success ACK.

Focused tests should execute original versus revised code with a controlled, observable AudioContext constructor: importing unused modules and activating an inactive sender should create no optimized context; a genuine source/destination/metronome/microphone/sender operation should create exactly one and preserve active graph operations, resume behavior, sample/routing bytes and subsequent singleton identity. Explicitly test existing source sender-role/shouldBeActive precedence, disabled/enabled transitions, per-output/PDF role, no-source volume updates, actual live analyser data changing without store events, teardown/reinitialization and failure propagation. Actual browser evidence is then needed: first programmatic activation without a user gesture, first playback/metronome/microphone/analyser and worklet transfer/capture on real WebKit, preserving accepted raw PCM and Opus continuity tests. Controlled constructors prove lazy ownership decisions, not physical audio hardware or browser audio capability. The identical-DOM-write meter optimization can be a second, smaller slice with the parity corpus above; it need not alter polling to remove those redundant writes.

Any further app/profile/ablation run waits for a new coordinator reservation. A separately authorized private-profile experiment may count future rAF callbacks and unchanged meter mutations with bounded observer state, or test unused AudioContext suspension while preserving real active playback as a control. Instrumentation and changed workloads must be labeled; they do not replace release acceptance. Do not mutate archived assets/binaries to inject instrumentation, and do not use a thread name alone as a sampled CPU stack.

After selecting and implementing a bounded optimization in a separately authorized source slice, keep exact original behavior tests and run real current-release before/after comparisons with fresh identical profiles, matching features and immutable distinct binary/source hashes. At least five alternating/randomized pairs, one warmup, 20+ seconds settle and 10+ seconds steady sampling are needed to assess variability. Keep PSS and observed CPU accounting, per-run raw data, engine/environment policy and cleanup coverage; report both favorable and unfavorable metrics. Archived `c9e62492` remains the historical partial-feature baseline and must not be silently replaced by a current build. No performance improvement is claimed by this investigation.

# Ordered FLAC comment blocks

This is a separate followup to the plain ID3 timestamp correction. The unchanged JPEG FLAC fixture/packaged source recording has two Vorbis-comment blocks: the first contains `TITLE=real container`, and the second contains the JPEG artists/album/date. Actual pinned music-metadata7.14.0 accumulates both in physical order. Lofty0.24 explicitly retains only the last block, so native common metadata previously lost that title. Source fixture bytes and the original GUI recording are unchanged.

The existing format preflight still validates the full declared structure of each comment block before its entries are retained. A private `flac_comments::Plan` accumulates ordered key/value entries during that same guarded pass. Lofty then performs its existing container/ID3 parse; the existing Collector receives leading ID3 first and all planned Vorbis entries second, at original priorities4 and3 respectively. Source duplicate scalar replacement, artists/unique-array ordering, unknown-tag handling, date/year derivation and insertion order remain the Collector's behavior. No second whole-file parser/pass, cover/image decode, new service, thread, queue, IPC, public command or owner is introduced. OGG and Opus collection stays unchanged.

Certified comments use canonical printable ASCII keys (0x20 through0x7d, excluding the separator) and valid UTF8 values. Keys are ASCII-uppercased; values preserve exact spaces, NULs, Unicode and additional equals signs. Empty values, empty blocks, trailing bytes after the declared list, intervening padding/application blocks and leading plain ID3v2.3/v2.4 are covered by real source comparisons. Noncanonical/empty keys, missing separators and invalid UTF8 are explicit `audio_unsupported_variant`, rather than guessing source replacement-decoding behavior or silently returning different text. Existing parser/container/ID3 limitations remain; this is not a full FLAC implementation.

Each retained block has already crossed the original allocation declaration/read/operation/deadline/cancellation checks. Across all FLAC blocks, the retained entry count must not exceed `tag_limit` before a new block's entries are copied. Owned key/value UTF8 bytes plus a conservative table-growth charge must not exceed `allocation_limit`, checked before each allocation. The table charge is four String-pair slots for the first entry plus two slots per subsequent entry; it covers the minimum four-entry vector allocation and growth. Valid UTF8 values need no replacement allocation; ASCII uppercase cannot expand the key. Original raw block allocations keep their separate existing size cap and are dropped after each append. Thus this new retained plan adds at most the configured charge, rather than treating per-block caps as an aggregate bound.

Defaults remain two fixed workers/shared whole-job-result permits,16MiB actual reads,50,000 read/seek operations,4MiB allocation/retained-plan charge,4096 entries,4MiB result and10s cooperative deadline. Trusted maxima remain unchanged. Combined ID3 and Vorbis collection also passes the existing overall Collector count and result guards. CPU copying/parsing is bounded by these counts/bytes; cooperative filesystem deadlines cannot preempt an OS call. No ready-result disposal, cancellation fence, snapshot, immutable-file or shutdown-join claim is added. Existing held-descriptor observations, sequential reuse, caller-drop retention and actual worker joins are unchanged and their tests still pass.

The source accepts some malformed inputs that native deliberately rejects. In the new evidence corpus, a UINT32_MAX field length clamps to available bytes in the source, while native rejects its declared resource size. A truncated last comment block is silently discarded by the source, preserving earlier metadata; native returns input rejection instead of publishing a partial plan. Huge vendor/count declarations fail in the real source as well. Aggregate-count and retained-allocation overflow are explicit native resource limits even where source parsing succeeds. A late structural/encoding/resource failure returns no partial plan or common metadata.

Six new source suites execute original `audio.ts::getAudioMetadata` and `nowPlaying.ts::getAudioMetadata` with actual installed music-metadata and real generated containers. They compare ordered typed common metadata, including NaN/Infinity/signed zero before projection, and separately the compatibility JSON projection. The latter normalizes both sides with JSON.stringify/parse; it does not certify byte-for-byte numeric serialization (notably negative-zero spelling). Native serialization itself is not changed. Source callback object identity/filePath and exact original helper use are checked. Pictures are excluded only at the top-level comparison because this parser intentionally reports CoverKnowledge::Unknown; the separate cover/image backend owns those bytes.

New coverage:9 fully compared files,21 sequential opened passes (including three on the held original after pathname replacement),9 public JSON replies,2 actual source parse failures,6 guarded malformed/resource inputs,3 explicit encoding/key unsupported cases and4 source-accepted/native-guarded cases. The exact packaged JPEG FLAC raw recording is independently compared excluding pictures; original file hashes are checked before/after. Five new Rust tests cover original Collector priority/order, cumulative count/allocation across individually small blocks, late malformed declarations without partial results, unsupported encodings/keys and real Budget read/operation/cancellation enforcement.

Validation:32 Rust tests and21 Node source suites pass (6 new FLAC,6 prior ID3,9 unchanged metadata/opened suites), strict all-target Clippy, rustfmt, Prettier and Windows GNU/macOS ARM library compile checks. Cross checks establish compilation only; actual platform execution and GUI acceptance belong to coordinator integration. No app, Electron/Xvfb run, root build or root binary is used by this slice.

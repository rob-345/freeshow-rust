# Timecode routing and LTC lifecycle preparation

This pure crate ports `src/electron/timecode/timecode.ts` and the routing/frame/lifecycle logic of `LTC.ts` from immutable Electron commit `2d94defcf98175e4f5c9504e7f4fd1d33c35c975`. It creates no runtime, threads, audio device, MIDI port or usable codec. No shared IPC, frontend, native host or CI is wired by this commit. Retained Svelte payloads remain unchanged.

## API and later host boundary

Use one `Router::new(is_windows)` per captured native runtime/library run, on one bounded ordered host stream:

```rust
let step = router.begin(Command::Start {
    kind: "receive".into(), mode: "MTC".into(),
    framerate: Scalar::number(25.0), data: Data::Json(settings),
})?;
// Execute each trusted effect on the real bounded IO owner. Retain the router,
// token and accepted real handle through caller Drop and context retirement.
let next = router.complete(&effect_token, Completion::Opened)?;
```

`Step.effects` contains source notifications and trusted host intents. There is no success ACK. `EffectToken` and `ListenerToken` cannot be deserialized or constructed from their serialized diagnostic ID. Tokens also carry a private router identity: foreign, repeated, wrong-kind and stale completions reject without releasing a pending owner. Oversized buffers reject without consuming the token; after disposing actual native resources, the host must provide a real failed receipt instead.

`begin` routes typed `Start`, `Stop`, `Value`, `Status` and `Audio`. `accept_listener(open_token)` records a real accepted input before its async open/connect promise finishes, returning the token for early callbacks; duplicate acceptance rejects. Completing `Opened` registers that listener in the ordinary receiver map. Failure after acceptance preserves the real handle as an owned orphan. `accept_sender(send_token)` similarly records an accepted retained MTC output when a later send might fail. Successful send completion conservatively retains that output until a real `StopMtc` receipt.

`mtc_message(listener, bytes, now_ms)` reuses `freeshow-midi::MtcReceiver`; `now_ms` supplies the source `Date.now()` clock. All modes share its existing `StatusGate`. MTC packet generation and physical port selection/open/send/close remain the existing MIDI foundation and future host's responsibility; `SendMtc` preserves raw framerate/data for that boundary. This crate does not duplicate the MTC packet algorithm or pretend a planned open succeeded. MTC output open/cache internals remain delegated: the future host must serialize output ownership on the existing MIDI owner or account for every concurrently accepted output there. The router tracks the retained output-binding obligation, not individual JZZ output handles; source concurrent `openMidiOut` races and physical output delivery are not certified by these routing tests. A terminal StopMtc receipt must mean that owner has retired all output ownership for this router/run; a source STOP still follows the source current-port behavior.

One synchronous source continuation may be pending while up to eight source async MTC opens/sends/closes are pending. The host must settle synchronous constructor, decode/encode and STOP effects before dispatching the next ordinary source command/callback or async source completion. The API rejects such interleaving without consuming authority. Native OS acceptance can still be recorded while its source promise waits. This preserves the source JavaScript call-stack ordering without creating a task per frame or an internal unbounded deferred-event queue. The future host must bound its own raw callback queue and retain accepted IO independently of a caller future.

Notifications map to `MAIN/TIMECODE_VALUE`, `MAIN/TIMECODE_STATUS`, `MAIN/TIMECODE_AUDIO_DATA`, or source `ToMain.ALERT`; none gets an invented listener reply. Incoming `TIMECODE_STATUS` only logs its original data. It does not call the status gate. `Number` and `Data::Undefined` preserve IEEE NaN/infinities/negative zero and top-level undefined as data-only values. The eventual bridge must hydrate those values after full context acceptance; JSON null or omission is not an equivalent transport claim.

## Preserved decisions and source quirks

Shared framerate starts at 25 and updates on JavaScript truthiness before routing even an unknown type/mode or deduplicated receive. Missing/null/false/zero/negative zero/empty string/NaN retain it; truthy scalar strings/booleans/numbers remain their original type. Decoder framerate is separate from shared send framerate. Mode and send data persist after STOP, so a subsequent VALUE can send/create an encoder again. STOP does not reset last status or emit stop/status/ACK. Every processed frame emits; only repeated status values deduplicate.

Receive deduplication applies to installed receiver-map entries, in insertion order. Pending MTC opens are not deduplicated. An open can complete after STOP and register itself; two completions can overwrite the same map entry. The native accounting retains all accepted overwritten handles, even though the source leaks their map ownership. An older accepted listener's callbacks still feed its own MTC state and the shared status gate until it is closed/retired. STOP closes the current sender first, then current receiver entries in source order. A thrown sender close prevents receiver stops. A thrown receiver close aborts the remaining sequence and preserves the source map, including already-stopped entries; closed tombstones keep their source dedup behavior until a successful reset/retirement.

LTC receiver construction is lazy: `LTCDecoder(48000, framerate, "u8")`. A real constructor failure sets a sticky decoder-failed flag, emits the exact source ALERT with the Windows Visual C++ suffix, and future attempts return without constructing or changing decoder framerate. Feed writes its bounded bytes then reads **one** frame; it does not drain an arbitrary decoder queue. The emitted time is `(hours*3600 + minutes*60 + seconds + frames/decoder_framerate)*1000`, without clamping or added drop-frame correction.

LTC sender construction is lazy: `LTCEncoder(48000, framerate)`; it resets if absent, raw framerate is not strictly equal, or time moves backward. Negative zero equals positive zero for the reset decision. A failed replacement preserves the old encoder/current framerate/last time and permanently sets the encoder-failed flag. Successful initialization precedes updating last time, then `setTimecode({hours,minutes,seconds,frames})`, `encodeFrame()`, and `getBuffer()`. Only a real `Encoded(bytes)` receipt emits those bytes. Set/encode/buffer failures preserve the source state reached before the failing call and do not set the constructor-failed flag. STOP clears encoder/last time but retains current framerate and sticky failure state. A host executing `CreateEncoder { replacing:true }` must initialize the replacement and settle ownership of the previous codec before accepting its completion; failed construction retains the previous codec.

The installed `libltc-wrapper` 1.1.2 JavaScript wrapper adds details a later real backend must preserve: encoder default `LTC_USE_DATE=1`; decoder queue default 32 and `48000/framerate` samples per video frame, with the C boundary converting that value to int32. Its JavaScript decoder rejects framerate above 30. More subtly, FreeShow passes plural `frames`, but wrapper `setTimecode` adds default singular `frame:0` and the C addon reads **singular `frame`**. This planner deliberately preserves the original plural field rather than silently correcting it. The new test executes the installed wrapper JavaScript against a controlled addon boundary and verifies those arguments/defaults; that is not native codec/waveform evidence.

## Terminal retirement and bounds

`retire()` is a native terminal lifecycle distinct from the source's reopenable STOP. It rejects new commands, suppresses retired source frame/status/audio/constructor alerts, requests cancellation of all outstanding open/send/synchronous effects, and emits bounded close intents for every accepted listener/encoder/MTC sender. Pending IO remains pending until its actual completion receipt. Late successful opens are immediately issued real close intents instead of entering the source receiver map. A failed close retains its ownership and reports an error without emitting an immediate retry from that failure receipt. Another explicit `retire()` or independent real completion advances a bounded retirement pass. The host must collect all error receipts, retain their diagnoses, and bound its own retry/deadline policy rather than repeatedly executing a failed close in a tight loop. Native cancellation is a request, never a drain receipt. `drained()` requires all pending operations gone and every known accepted listener/codec/output retired. A future host must keep the router and actual IO owners alive through this condition; dropping this pure data structure performs no OS cleanup.

There are at most eight listener reservations (pending/accepted/overwritten/tombstone), eight async effect slots, and one synchronous effect slot. Retirement uses available slots and advances as real receipts free them; even a full async pool does not lose a listener or allocate another queue. A retirement step has at most nine effects. Audio input and encoded output are limited to 65536 bytes; MIDI messages reuse the foundation's 1024-byte limit. Start kind is limited to 32 bytes, mode/scalar text to 4096 bytes; send data is bounded before cloning to 1024 nodes, depth eight and 65536 aggregate UTF-8 string/key bytes. Error receipts are normalized to 1024 UTF-8 bytes. Checked 64-bit token IDs never wrap. No IO, scheduler, thread or process is hidden in these operations. The data-only parity CLI also bounds input, scripts/actions, per-action work and aggregate output.

## Evidence and limits

Focused checks: 13 Rust tests and 10 Node source/wrapper suites. Differential coverage runs 36 scripts/328 actions with 79 controlled constructor calls and 135 buffer intents. It executes the actual pinned `timecode.ts`/`LTC.ts` functions in separate CommonJS module contexts; one suite also executes actual pinned `MTC.ts` with controlled JZZ open/connect promises and explicit clock samples. Test instrumentation observes async rejection and snapshots lexical source state without replacing the algorithms. A full event-loop checkpoint settles the controlled promise chain before comparing the matching host completion. Captured constructor console errors are distinguished from propagated stop/write/encode failures in raw source evidence; neither is treated as an invented renderer ACK.

Rust tests cover foreign/duplicate/mismatched tokens, early real acceptance, async completion/callback barriers, late-open STOP/restart/overwrite, receiver tombstones, accepted connect failure, failed retirement close retry, late constructor retirement, retained/late MTC sender ownership, full-capacity retirement of all handles/codecs, bounded buffers/JSON/errors and rejection without losing continuation authority. Strict Clippy/Rustfmt and Windows GNU/macOS arm64 library cross-checks pass; execution evidence is Linux only.

[Native LTC probe](../../../crates/freeshow-timecode/fixtures/native-ltc.json) records Node v22.21.1, installed wrapper version/checksums and actual `MODULE_NOT_FOUND` for `../build/Release/ltc-native`. No package install, codec build, hardware port or audio waveform/device was substituted. Real LTC encode/decode, native allocator safety, date/BGF behavior, sample waveform parity, device playback/capture and OS scheduling remain unavailable. Existing native MIDI ports ignore SysEx before backend accumulation, so integrated full-frame MTC remains a separate gap even though the pure receiver understands those packets.

Typed scalar routing/arithmetic is covered, including nonfinite values and strings under controlled constructors. Complex/custom object coercion, malformed outer payloads/statuses, malformed decoder frame fields, non-JSON send data and renderer structured-clone/binary hydration remain explicit future-host unsupported/validation cases. Raw framerate strings must not simply be normalized before the MTC fps-code property lookup; the existing numeric packet API certifies numeric framerates, and a future adapter must either preserve that source distinction or reject the unsupported variant explicitly. Extreme/invalid fps values are only arithmetic/constructor-intent evidence: a real backend needs its own hard native allocation/sample limits before constructing anything. This planner's memory bounds do not establish libltc's internal safety or codec availability. There is no GUI, hardware, production IPC or playback parity claim in this slice.

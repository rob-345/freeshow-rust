# Plain ID3 timestamp text recovery

This correction addresses the unchanged `jpeg-apic` MP3 fixture that failed the native JPEG GUI run before any image decoding. The pinned original FreeShow helper (`2d94defcf98175e4f5c9504e7f4fd1d33c35c975`, music-metadata7.14.0) accepts its `TDRC="invalid"`, preserves `date:"invalid"` and has no own year property. Lofty0.24 default and Strict parsing reject that frame with `BadTimestamp("Timestamp segment contains non-digit characters")`. Replacing only the date text makes Lofty accept the file, including its unchanged NUL-separated artist text. Relaxed mode discards the date, so it is not a compatible repair. Invalid `TYER` is a distinct source case: its own year is NaN and remains typed NaN before the existing JSON projection.

After the existing structural ID3 preflight, a private bounded Read+Seek view maps plain leading timestamp frame IDs (`TDEN`, `TDOR`, `TDRC`, `TDRL`, `TDTG`) to collision-free text IDs. Lofty still performs text decoding and ordinary metadata parsing. Collection restores each original ID before the unchanged common mapper/priority logic. Every occurrence has a distinct alias, retaining source duplicates and physical order instead of Lofty's timestamp normalization/deduplication. Original IDs, including unknown text IDs occupying aliases, are reserved first. The underlying File is never written, cloned or replaced; the adapter overlays only the four ID bytes returned by each real budgeted read, including partial reads and arbitrary seeks.

The certified timestamp text encodings are Latin1 (0), BOM-marked UTF16 (1) and UTF8 (3), in ID3v2.3 and2.4. The source's generic v2.3 timestamp text preserves surrounding whitespace and embedded NULs; v2.4 splits NULs and trims each value. These differences, date/year derivation and original priority are retained. BOM-less encoding2 is explicitly `audio_unsupported_variant`: pinned music-metadata decodes it as UTF16LE while Lofty decodes UTF16BE. Tests retain that actual source distinction rather than claiming matching text. This narrow change does not implement a second text decoder.

Only zero-status/zero-format-flag timestamp frames are adapted. Existing canonical status-flagged timestamps remain accepted; invalid flagged timestamps remain an explicit Lofty input-rejection gap. Multiple consecutive leading ID3 tags with active recovery are explicitly unsupported, avoiding cross-tag alias collisions. Embedded WAV ID3 timestamp recovery, ID3v2.2, unsynchronization, extended headers, chapters, compressed/encrypted frames, malformed text and all other previously unsupported variants are not newly certified. Public errors/projection and skip-covers Unknown semantics remain unchanged; this fix does not establish image decoding, cover extraction or playback parity.

The original preflight runs before aliases, and all reads/seeks still cross the same operation/read/deadline/cancellation budget. The plan checks the combined occupied-ID and patch-table charge before allocating; it is capped by the existing allocation_limit and tag_limit. Defaults remain two workers/jobs,16MiB reads,50,000 operations,4MiB allocation,4096 tags,4MiB result and10s cooperative deadline. At default tag count the tables charge at most81,920 bytes (4 bytes per original ID plus16 per recovered frame); the source block still has its original separate4MiB declaration cap. Trusted maxima remain16,384 tags/16MiB allocation, and the finite36^3 alias space is exhausted explicitly rather than looping indefinitely. No worker, queue, ready-result ownership, descriptor observation, public command or shutdown semantics change.

The new independent Node suite executes both original helpers with the real installed parser on unchanged/generated MP3 bytes and compares the native typed common object recursively, including insertion order, own undefined/nonfinite values, and separately the legacy public JSON projection. It checks the actual packaged JPEG source recording excluding separately owned pictures, duplicate dates/priority/aliases, v2.3/v2.4 encodings and whitespace, flagged gaps, huge/truncated/encrypted/recursive declarations, and three sequential reads of a held descriptor after path replacement. Original bytes are independently hashed before/after. The existing source suites remain unchanged. No Electron app/GUI or root binary is run/modified by this slice.

The new source coverage is26 fully compared files,55 sequential opened passes,26 public replies,4 explicit unsupported/input gap cases and5 guarded malformed/resource inputs. Cross checks establish compilation, not actual platform execution.

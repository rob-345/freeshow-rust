# Linux desktop Spotify commands

This is a native transport foundation for `MAIN.SPOTIFY_COMMAND`; no production IPC, bridge, account integration, or desktop Spotify session is installed by this patch. Base: `06501c09`. The immutable parity oracle is `2d94defcf98175e4f5c9504e7f4fd1d33c35c975` (`1.6.7-beta.2`), using actual `executeSpotifyCommand`, its `mainResponses` handler, and `receiveMain`. The new oracle checks normalized-LF SHA256 of all three original files, extracts the handler/function from the TypeScript AST, and executes their actual bodies. Local source runtime: official standalone Node 22.21.1; this is not Electron's distinct V8/ICU runtime.

## Native API and host obligations

```rust,ignore
let prepared = PreparedCommand::new("seek", Some(seconds))?;
let accepted = service.begin_command(&owner, prepared, deadline)?;
let control = accepted.control(); // cancel()/settled(); NO job lease or owner thread
let original_reply = accepted.reply(&owner)?; // true: accepted queue scheduling only
// Publish MAIN { channel: "SPOTIFY_COMMAND", data: true }, original listenerId.
// The source public reply is NOT delayed until this optional native observation:
let finished = accepted.finish().await?;
let actual = finished.result(&owner)?; // borrowed while retaining its quota
```

`Owner` remains the native snapshot and opaque per-service transport seal (the existing host freezes its initial snapshot for a long-lived service, not as a current-library assertion); a byte-identical independently constructed owner cannot access a receipt. Prepared commands, receipts, and controls are not deserializable executable/session authority. The host validates main-window role, exact current full request context, bounded ignored payloads, and numeric input shape before calling preparation. The native executable and captured session/locale are supplied only through the existing trusted `Backend`. No executable, shell text, session bus, object path, or environment comes from a command payload. The new local dependency is already-locked `ryu-js = 0.2.2`; coordinator updates the root package lock graph.

The host must publish only `accepted.reply(...)` as the original response, then either retain a bounded actual-completion observer or deliberately drop that observer. Neither dropping the early receipt nor dropping/aborting its `finish` future cancels the actual accepted work. The actual work independently retains its whole-job permit. `CommandFinished` keeps that same permit through borrowed native outcome inspection until actual consuming disposal. There is no second source success ACK or invented completion event. Only an `Ok(CommandFinished)` is a typed completed-job result: a lost-result-channel `Err` alone is not cleanup proof; use the retained control settlement witness and actual service join.

To cancel obsolete queued/entered intent, the host keeps at most four native `CommandControl`s with each actual request's full `RuntimeContext`, prunes only controls whose `settled()` is true, and explicitly calls `cancel()` on context retirement/CLOSE. The handle owns no job permit and does not cancel on Drop. It cannot cancel another run or prolong the owner thread. `settled()` means the actual job has no remaining direct child/seek continuation, including supervised panic cleanup; it does **not** mean a public result was disposed, an already-sent D-Bus effect was undone, or the native thread was joined. Do not substitute the process-global service identity for the request context. The production host and its retained request registry remain coordinator-owned.

Known unsupported platform/session and known failed executable capability reject command admission before an early true. Initial pending capability may admit a bounded queue job; the actual fixed owner probes it before effects. A later executable disappearance can still fail after early scheduling. That updates cached capability; a new actual state query retains the existing reprobe/recovery behavior, or the host can retire/recreate the service after real join. Commands do not silently bypass a known unavailable cached capability. The existing state API and its cancellation-on-ticket-Drop policy remain unchanged.

## Source-compatible command subset

The four exact names `playpause`, `next`, `prev`, `pause` produce the actual source Player method names. Their unrelated value (including objects/null) is ignored; the host must only decode a numeric value for `setVolume`/`seek`, rather than reject unused value shapes. `setVolume` accepts a finite native binary64 Number and uses JavaScript Number-to-string formatting, including `-0 -> "0"`, subnormals, and exponent spelling. `seek` uses source multiplication by one million and `Math.round` (ties toward positive infinity), restricted to a finite scaled value within `±(2^53-1)`. Host JSON decoding must supply the intended source binary64 Number; the private driver supports explicit IEEE input bits to avoid testing serde's decimal parser instead of this operation. No clamping or latest-value latch is added.

Source accepts additional coercions (`null`, strings, booleans), silently ignores unknown commands/missing numeric values, and can interpolate unsafe track IDs into a shell. This bounded API explicitly rejects those unsupported numeric/command cases and unsafe IDs; it never returns fake true for them. Plain missing numeric input means source `undefined`; it is distinct from JSON null. Mac/Windows command backends remain explicit unsupported.

Seek performs a real Metadata read, then applies the source's first-match regex. It accepts only `variant string` track IDs; a standard MPRIS `variant object path`, absent key, or empty capture results in `MissingTrackId` and **no** SetPosition child. The exact ECMAScript whitespace set is retained, including FEFF and excluding NEL. Captured IDs are restricted to valid D-Bus ASCII object paths (`/` or nonempty alphanumeric/underscore components), at most 1024 bytes. Otherwise the completion is explicit `spotify_command_unsupported`, rather than shell interpolation or a fabricated send.

`CommandOutcome::Sent` proves the direct `dbus-send --type=method_call` process exited successfully after the send attempt. The original command deliberately has no `--print-reply`, so this is not proof Spotify applied the effect. Seek metadata failures retain `SourceProcessFailure { service_unknown }`; ServiceUnknown is separately classified as the source's suppressed diagnostic, and other process errors remain observable. Static bounded errors/counters retain no stderr, session address, or extracted metadata. `MissingTrackId` is a real source no-followup outcome, not fabricated backend availability.

## Ownership and resource bounds

One existing fixed native thread and current-thread Tokio runtime own the transport. There are no per-command Tokio tasks, new threads, idle timers, or a separate command runtime. A `FuturesUnordered` contains at most four whole jobs shared with the unchanged sequential state-query lane. Independent command children and seek continuations can progress while another seek or state query is waiting; concurrent effect order beyond actual observed source turn/continuation boundaries is not universally prescribed.

The existing process-global four whole-job permits cover queued, active, early-replied, completed/uncollected and borrowed results across service replacement. The existing four lifecycle observer slots and native-owner exclusion remain. Each command uses the existing configured total `query_timeout` (default 2 seconds, maximum 10 seconds), including queue wait, capability retry, metadata and followup process. The stdout/stderr budgets (default 256/64 KiB, hard 1 MiB/256 KiB) are shared across both seek children; optional capability probes have their separately bounded 8/8 KiB pipes. Arguments have constant count and bounded text; no shell is invoked by Rust. Native OS spawn/wait operations are not hard preemptible.

The child registry lives outside both individual guarded futures and the guarded aggregate scheduler. It retains the actual child, a separate whole-job quota anchor, and entered-job settlement witness. A panicking/dropped future cannot release the only child/permit before outer cleanup actually kills and waits. Before entry, discarded queued work can truthfully mark no-effects settlement; after entry, only actual normal completion or the outer cleanup may do so. A held seek can have its real child killed but cannot have an already-sent Player effect undone.

Status separates `activePid` (query/probe) from at most four `commandPids`; `spawned/reaped` cover all actual direct children. `commands/commandsCompleted/commandFailures/lastCommandError` are bounded scalar diagnostic observations. Completion counters precede final local frame disposal and are not event-flush or quota-release barriers; an aggregate owner panic may settle effects without sending normal per-job result completions. `drained` requires actual native thread join, no query/command PIDs, and all spawned children reaped. It is not inferred from done-watch, a result, a control flag, or a canceled wait. Existing timeout/observer-Drop retry retains the same real JoinHandle, with sticky panic errors. Last-owner synchronous Drop remains an emergency cleanup boundary; normal hosts explicitly await actual shutdown rather than block an async executor by dropping their last service owner.

## Evidence and limitations

All live fixtures use a private `dbus-daemon` with no service activation directories and an actual private GIO MPRIS peer. Its session address is supplied only to the native fixture and the actual original shell commands. Tests own and await daemon, peer, original shell children, and native-driver close; nothing connects to the desktop Spotify bus. Peer side effects are awaited as actual stdout events, never inferred from status or no-print-reply process exit.

Focused checks use the private `/mnt/data/cache/freeshow-rust-build/spotify-commands/target`, jobs=1, debug=0, incremental=0 and an external standalone manifest importing these actual sources/fixtures. No root/shared Cargo files or targets are modified. Commands:
